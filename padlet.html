🌱 초급 — 제미나이로 대화만으로 수업용 시뮬레이션 만들기

준비물: 구글 계정 (제미나이 무료 버전) 예상 소요: 30~40분 결과물: 제미나이 공유 링크

코드를 한 줄도 안 봐도 됩니다. "이런 걸 만들고 싶다"를 구체적으로 말로 설명하고, 나온 결과를 보면서 계속 다듬어가는 것이 전부예요.

  1. gemini.google.com에 구글 계정(학교 계정도 가능)으로 로그인합니다.
  2. 입력창 근처의 "도구"(＋) 버튼을 눌러 Canvas(캔버스) 모드를 켭니다. 캔버스 모드에서는 결과가 별도 화면에 코드/미리보기 형태로 나와서 수정하기 훨씬 편해요.
  3. (선택) 입력창 근처 모델 모드도 상황에 맞게 골라보세요 — 간단한 요청은 ⚡ 빠른 모드, 복잡한 요청은 🧠 사고 모드가 더 꼼꼼합니다.
  4. 프롬프트를 쓸 때 이 4가지를 포함하면 결과가 훨씬 좋아집니다: ① 무엇을(과학 개념) ② 누구를(대상 학년) ③ 어떻게 조작할지(슬라이더/버튼/입력값) ④ 무엇을 보여줄지(그래프/애니메이션/숫자) — 그리고 맨 끝에 반드시 "html로 만들어줘"를 붙이세요. 이 말이 있어야 브라우저에서 바로 열어볼 수 있는 완성된 코드로 나옵니다.
    중학교 2학년 대상으로 옴의 법칙(V=IR) 시뮬레이터를 만들어줘. 전압과 저항을 슬라이더로 조절하면 전류가 실시간으로 계산되고, 회로 애니메이션이랑 V-I 그래프도 같이 보였으면 좋겠어. html로 만들어줘.
    고등학교 지구과학 수업용으로 태양계 행성들의 공전을 3D로 보여주는 시뮬레이터를 만들어줘. 공전 속도를 조절할 수 있고, 각 행성을 클릭하면 이름과 거리 정보가 나왔으면 해. html로 만들어줘.
    중학교 3학년 화학 수업용 몰농도 계산기를 만들어줘. 용질의 질량과 몰질량, 용액의 부피를 입력하면 몰농도가 계산되고 단계별 풀이 과정도 같이 보여줘. html로 만들어줘.
    고등학교 생명과학 수업용 먹이사슬/개체수 변화 시뮬레이션을 만들어줘. 포식자와 피식자 초기 개체수를 입력하면 시간에 따른 개체수 변화 그래프가 애니메이션으로 그려졌으면 좋겠어. html로 만들어줘.
  5. 결과가 마음에 안 들면 코드를 고치려 하지 말고 "이 부분을 이렇게 바꿔줘"라고 계속 대화하세요. 캔버스는 대화를 이어가면서 같은 코드를 계속 고쳐나갈 수 있어요. 스크린샷을 그대로 보여주면서 "여기가 이상해"라고만 해도 충분합니다.
  6. 완성되면 화면 위쪽 공유 버튼으로 링크를 만들어 갤러리에 제출하세요. 공유 링크가 잘 안 만들어지면, 다운로드 아이콘으로 받은 .html 파일을 갤러리 제출 폼에 그대로 첨부해도 됩니다.
💡 팁 처음부터 완벽한 프롬프트를 쓰려 하지 마세요. 일단 대충 요청해서 나온 걸 보고 "이건 되네, 이건 이렇게 바꾸자"로 다듬는 게 더 빠릅니다.

🔌 중급 — API로 진짜 세상 데이터 가져오기

준비물: 구글 계정 (제미나이) 예상 소요: 30~40분 결과물: 실제 데이터를 보여주는 시뮬레이션

초급이 "내가 만든 화면 안에서만 동작하는" 도구였다면, 중급은 실시간으로 바뀌는 진짜 데이터(날씨, 급식, 천문 정보 등)를 가져와 보여줍니다. 이때 쓰는 창구가 API예요 — "정해진 방식으로 물어보면 답을 알려주는 곳"이라고 생각하면 됩니다. 내가 직접 만든 데이터만 쓸 수 있는 게 아니라, 이미 다른 기관이 실시간으로 관리하는 데이터를 그대로 "빌려와서" 보여줄 수 있어요.

  1. 먼저 보조자료 탭의 "바로 써먹는 API 모음"에서 쓰고 싶은 API를 하나 고릅니다. 오늘은 인증키가 필요 없거나, 무료로 즉시 발급되는 것 위주로 골라보세요.
  2. 인증키가 필요하다면 해당 사이트에서 "활용신청"/"인증키 신청" 메뉴로 무료 발급받습니다 (보통 즉시~1~2일 내).
  3. 제미나이 캔버스에서 아래 틀을 채워 요청합니다.
    [API 이름] API를 fetch로 불러와서 보여주는 html을 만들어줘. API 주소(엔드포인트)는 [API 문서 링크]이고, 필요한 인증키는 [발급받은 키]야. 가져온 데이터로 하고 싶은 것: [예: 오늘부터 3일간 우리 지역 날씨를 카드 형태로 보여줘] html로 만들어줘.
  4. 바로 써볼 수 있는 예시 두 가지:
    공공데이터포털의 기상청 단기예보 API를 fetch로 불러와서, 오늘부터 3일간 우리 지역 날씨(기온/강수확률)를 카드 형태로 보여주는 html을 만들어줘. API 주소는 [발급받은 엔드포인트], 인증키는 [발급받은 키]야. html로 만들어줘.
    NASA APOD API(https://api.nasa.gov/planetary/apod?api_key=DEMO_KEY)를 fetch로 불러와서, 오늘의 천문 사진과 설명을 보여주는 html을 만들어줘. 사진을 클릭하면 크게 볼 수 있었으면 좋겠어. html로 만들어줘.
    GBIF API(https://api.gbif.org/v1/occurrence/search)를 fetch로 불러와서, 학명을 입력하면 그 생물의 실제 관측 기록을 지도 위에 점으로 표시하는 html을 만들어줘. 예시로 왜가리(Ardea cinerea)로 검색해줘. 좌표는 decimalLatitude/decimalLongitude 필드를 쓰고, 각 점을 클릭하면 관측 날짜와 사진(media 필드)이 보였으면 좋겠어. 지도는 Leaflet 라이브러리를 CDN으로 불러와서 써줘. 인증키는 필요 없어. html로 만들어줘.
    Open-Meteo API(https://api.open-meteo.com/v1/forecast)를 fetch로 불러와서, 위도/경도를 입력하면 그 지역의 현재 기온과 오늘의 최고/최저 기온을 보여주는 html을 만들어줘. 예시로 서울(위도 37.5, 경도 127.0)로 검색해줘. 인증키는 필요 없어. html로 만들어줘.
    USGS 지진정보 API(https://earthquake.usgs.gov/fdsnws/event/1/query?format=geojson)를 fetch로 불러와서, 최근 일주일간 규모 5.0 이상 지진들을 지도 위에 점으로 표시하는 html을 만들어줘. 점 크기는 지진 규모(mag)에 비례하게 하고, 클릭하면 위치명(place)과 발생시각이 보였으면 좋겠어. 지도는 Leaflet 라이브러리를 CDN으로 불러와서 써줘. 인증키는 필요 없어. html로 만들어줘.
    ISS(국제우주정거장) 실시간 위치 API(https://api.wheretheiss.at/v1/satellites/25544)를 fetch로 불러와서, 세계지도 위에 ISS의 현재 위치를 표시하는 html을 만들어줘. 고도(altitude)와 속도(velocity), 낮/밤 여부(visibility)도 숫자로 보여주고, 5초마다 자동으로 새로고침해서 움직이는 것처럼 보이게 해줘. 지도는 Leaflet 라이브러리를 CDN으로 불러와서 써줘. 인증키는 필요 없어. html로 만들어줘.
    NASA 소행성 접근정보 API(https://api.nasa.gov/neo/rest/v1/feed?api_key=DEMO_KEY)를 fetch로 불러와서, 오늘 하루 지구에 근접하는 소행성 목록을 카드 형태로 보여주는 html을 만들어줘. 각 카드에는 소행성 이름, 예상 크기, 지구와의 최근접 거리, 위험 여부(is_potentially_hazardous_asteroid)를 표시해줘. html로 만들어줘.
    PubChem API(https://pubchem.ncbi.nlm.nih.gov/rest/pug/compound/name/)를 fetch로 불러와서, 화합물 이름(영어)을 입력하면 분자식, 분자량, IUPAC 명칭을 보여주는 html을 만들어줘. 예시로 caffeine을 검색해줘. 인증키는 필요 없어. html로 만들어줘.
  5. 완성되면 초급과 똑같이 공유 버튼으로 링크를 받아 갤러리에 제출하세요.
💡 팁 오늘 다루는 API들은 인증키가 코드에 그대로 보여도 큰 문제가 없는 무료·공개용 키예요. 로그인 정보처럼 진짜 안전하게 숨겨야 하는 값은 다음 단계(고급)에서 서버에 숨기는 법을 배웁니다.

🚀 고급 — Apps Script로 제출 페이지 만들고 배포하기

준비물: 구글 계정 + 제미나이 예상 소요: 40~50분 결과물: 데이터가 쌓이는, 배포된 웹앱

지금까지는 "혼자 쓰는" 도구였다면, 고급은 "학생들이 제출하면 데이터가 쌓이는" 진짜 웹앱입니다. 구글 스프레드시트를 데이터 저장소로, Apps Script를 서버로 씁니다 — 서버비 없이 이미 있는 구글 계정만으로 가능해요.

🎯 이미 뭘 만들지 정했다면, 이렇게 바로 요청해도 됩니다

위 지침서는 처음부터 하나씩 안내받고 싶을 때 쓰는 것이고, 이미 스프레드시트와 원하는 항목이 정해졌다면 아래처럼 한 번에 요청해도 좋습니다. (참가자 사전 설문 예시)

구글 스프레드시트(https://docs.google.com/spreadsheets/d/1hdSA0oZq4JYGn0J2dihZavxZ6kET7FEGiVzyVrEB0vM/edit)에 있는 명단을 가지고 간단한 설문 html 페이지를 만들고 싶어. Apps Script를 활용할 거니까 Code.gs와 html을 각각 만들어줘. 사용자가 이름을 치고 들어가서 아래 질문에 답변을 하면, 위 스프레드시트에 답변이 쌓이게 해줘. 1. (드롭다운) 코딩 또는 바이브 코딩 경험이 있나요? (수업·업무 등에 활용하고 있음 / 타 연수 등에서 실습만 해보거나 개인적으로 한두 번 시도만 해봄 / 경험이 없음) 2. (단답형) 상상하는 것을 마음껏 만들 수만 있다면, 어떤 것을 만들어보고 싶으신가요?

전체 흐름 한눈에 보기

  1. 빈 구글 스프레드시트를 만들고 링크를 AI에게 알려줍니다. (AI가 스프레드시트 ID를 알아서 찾아냅니다)
  2. 스프레드시트 메뉴 [확장 프로그램 → Apps Script]로 들어가서, AI가 준 Code.gs 코드를 통째로 붙여넣고 저장합니다.
  3. 왼쪽 파일 목록 "＋" → HTML로 새 파일을 만들고(이름을 AI가 알려준 것과 정확히 똑같이), 화면 코드를 붙여넣습니다.
  4. 오른쪽 위 [배포 → 새 배포] → 유형: 웹 앱 → 액세스 권한: "모든 사용자"로 설정 후 배포. 나온 URL을 화면 코드의 정해진 자리(APP_URL)에 다시 채워 넣습니다.
  5. 배포된 URL로 직접 접속해서 제출해보고, 스프레드시트에 잘 쌓이는지 확인합니다.

항목GitHub PagesApps Script

주소짧고 깔끔 (github.io/저장소명)길고 복잡 (script.google.com/macros/...)

언제 쓰나데이터 저장이 필요 없는 결과물, 또는 서버는 그대로 두고 주소만 예쁘게학생 제출처럼 데이터가 쌓여야 할 때

둘은 경쟁 관계가 아니라 같이 쓰는 조합입니다 — 서버(Apps Script)는 그대로 두고 화면(HTML)만 GitHub Pages로 옮기면, 데이터도 쌓이면서 주소도 예뻐집니다.

🤝 Claude Code 같은 에이전트를 쓴다면?

지금은 제미나이 채팅으로 진행하고 있어서 위 6단계를 전부 직접 클릭해야 합니다. 그런데 Claude Code 같은 에이전트를 쓰면, "깃헙에 이거 올려줘"라는 말 한마디로 2~6단계(저장소 생성, 파일 업로드, Pages 켜기)를 에이전트가 대신 실행합니다 — 사람이 직접 해야 하는 건 최초 1회 GitHub 로그인(브라우저 클릭이 필요해서 에이전트가 대신할 수 없는 유일한 부분)뿐입니다. 그 이후로는 "이 부분 고쳐줘"라고 말할 때마다 에이전트가 파일을 고치고 다시 올리는 것까지 자동으로 해줍니다.

💡 팁 Apps Script 대신 Firebase를 쓰면 이 자동 배포가 한 단계 더 편해지는데, 이건 뒤에 이어지는 콘텐츠에서 다룹니다.
🔁 Agent로 GitHub 업로드 자동화하기

Claude Code 같은 에이전트를 쓰고 있다면, 채팅창에 말만 해도 저장부터 배포 반영까지 끝납니다

이 둘은 일어나는 장소가 다른 별개의 두 단계입니다 — 헷갈리기 쉬운 부분이라 순서를 명확히 짚고 갈게요.

① 커밋(commit) — 내 컴퓨터 안에서 일어나는 일. 지금까지 고친 내용을 하나의 "버전"으로 내 컴퓨터의 기록(히스토리)에 저장하는 것입니다. 문서 프로그램의 저장 버튼과 비슷하지만, 나중에 "그때 그 시점"으로 되돌아볼 수 있는 기록이 남는다는 점이 다릅니다. 인터넷이 안 되는 상태에서도 할 수 있고, 이 시점에는 아직 GitHub 서버에는 아무것도 전달되지 않은 상태입니다.

② 푸시(push) — 그걸 GitHub 서버로 실제로 전송하는 일. 내 컴퓨터에 쌓아둔 커밋(버전)들을 GitHub 서버로 업로드하는 것입니다. 이 순간에 비로소 인터넷에 올라가고, 배포된 사이트(GitHub Pages)에도 반영됩니다.

그래서 순서는 항상 파일 수정 → 커밋(내 컴퓨터에 저장) → 푸시(GitHub로 전송)입니다. "커밋하고 푸시해줘"라는 말이 자연스러운 것도 이 순서 그대로이기 때문이에요. "GitHub이 알아서 커밋으로 저장해준다"는 건 흔한 오해입니다 — 실제로는 정반대로, 커밋은 순전히 내 컴퓨터 안에서 미리 만들어지는 것이고 GitHub은 그 결과물을 푸시로 전달받아 저장할 뿐입니다. (그래서 커밋 없이 푸시만 하는 것도 불가능합니다 — 푸시는 "이미 만들어진 커밋을 보내는 동작"이니까요.) 커밋만 하고 푸시를 깜빡하면, 변경 내용은 내 컴퓨터 안에만 남아있고 실제 배포된 사이트에는 반영되지 않습니다.

제미나이 같은 채팅형 AI는 이 두 단계를 사람이 GitHub 화면에서 직접 클릭해야 하지만, Claude Code 같은 에이전트를 쓰고 있다면 채팅창에 "이 부분 고쳐줘"라고 말만 해도 파일 수정 → 커밋 메시지 작성 → 커밋 → 푸시까지 에이전트가 전부 대신 실행합니다.

🔌 그 전에 — Claude Code를 GitHub에 처음 한 번 연결하기

Claude Code가 여러분 대신 GitHub에 파일을 올리려면, "이 컴퓨터의 Claude Code가 내 GitHub 계정을 대신 조작해도 된다"는 허락을 딱 한 번 받아야 합니다. 혹시 "토큰 같은 걸 직접 발급받아야 하나?"라고 생각하실 수 있는데, 그렇지 않습니다 — 복잡한 키·토큰 발급 과정 없이, 브라우저에서 로그인 한 번으로 끝납니다.

  1. Claude Code 채팅창에 "깃허브에 연결해줘"라고 요청합니다. (git과 GitHub CLI인 gh가 설치되어 있는지 먼저 확인하고, 없으면 설치 링크를 알려줍니다)
  2. Claude Code가 터미널에서 gh auth login을 실행하면, 브라우저 창이 뜹니다. 이 화면에서 실제로 로그인·승인 버튼을 누르는 것만큼은 사람이 직접 해야 합니다 — Claude Code가 대신 클릭할 수 없는 유일한 단계예요.
  3. 뜨는 선택지에서 "GitHub.com" → "HTTPS" → "브라우저로 로그인" 순서로 고르고, 이미 로그인되어 있는 GitHub 계정으로 승인을 완료합니다.
  4. 로그인이 끝났다고 Claude Code가 확인해주면, 그 다음부터는 이 연결 작업을 다시 할 필요 없이 저장소 생성·업로드·배포까지 전부 채팅으로만 처리할 수 있습니다.
너는 지금부터 이 컴퓨터의 Claude Code를 내 GitHub 계정에 연결하는 걸 도와주는 조수야. 나는 이런 걸 한 번도 안 해봤으니, 아래 순서를 한 단계씩만 진행하고 내가 "완료했어"라고 하면 다음 단계로 넘어가줘. 1) 먼저 이 컴퓨터에 git과 GitHub CLI(gh)가 설치되어 있는지 확인해줘. 둘 중 하나라도 없으면, 설치 링크(git: https://git-scm.com/download/win, GitHub CLI: https://cli.github.com/)를 알려주고 설치부터 하라고 안내해줘. 2) 설치가 확인되면 gh auth login을 실행해줘. 그다음 나한테 "GitHub.com" → "HTTPS" → "브라우저로 로그인" 순서로 선택하라고 안내해줘. 브라우저 창이 뜨면, 그 화면에서 실제로 로그인·승인 버튼을 누르는 것만큼은 내가 직접 해야 하는 유일한 단계라는 것도 미리 알려줘 (네가 대신 클릭할 수 없다는 것도 같이 설명해줘). 3) 로그인이 끝나면 gh auth status로 정상적으로 연결됐는지 확인하고, 결과를 나한테 짧게 알려줘. 4) 연결이 확인되면, 이제부터는 이 연결 작업을 다시 할 필요 없이 내가 "깃헙에 올려줘" 같은 말만 해도 저장소 생성부터 배포까지 대신 처리할 수 있다고 알려줘. 자, 이제 1번부터 시작해줘 — 먼저 git과 gh가 설치되어 있는지 확인해줘.
💡 팁 gh auth status로 지금 로그인이 되어 있는지 언제든 확인할 수 있습니다. 다른 컴퓨터로 옮기면 이 연결 작업은 그 컴퓨터에서 다시 한 번 해야 해요.

너는 지금부터 이 프로젝트 폴더에서 나를 도와주는 에이전트야. 앞으로 내가 파일을 고쳐달라고 요청할 때마다 아래 규칙을 지켜줘. [앞으로 지켜줄 것] 1. 내가 "이 부분 고쳐줘" / "이 기능 추가해줘"처럼 파일 수정을 요청하면, 파일을 실제로 고친 직후 다음을 전부 실행해줘: 무엇이 왜 바뀌었는지 한두 문장으로 커밋 메시지를 만들고, git add → git commit → git push까지 끝내줘. 매번 "커밋하고 푸시할까요?"라고 나한테 되묻지 말고 바로 진행해줘. 2. 단, 아래 경우에는 반드시 먼저 나한테 확인을 받고 진행해줘: 기존 파일을 통째로 삭제하는 작업, git 히스토리를 되돌리는 작업(reset --hard 등), 강제 푸시(force push). 이런 위험한 작업은 자동 처리 대상이 아니야. 3. 작업이 끝나면 "커밋 완료: (커밋 메시지 요약)"처럼 짧게 결과만 알려줘. 매번 git 명령어 전체를 나한테 보여줄 필요는 없어. 4. 혹시 아직 이 폴더가 GitHub 저장소와 연결되어 있지 않다면, 먼저 나한테 GitHub 계정 아이디를 물어보고, 새 저장소를 만들어서 연결하는 것부터 진행해줘. 5. 이 다섯 가지 규칙을 이 프로젝트 폴더의 CLAUDE.md 파일에 정리해서 저장해줘 (파일이 없으면 새로 만들어줘). 그래야 나중에 내가 새 대화를 열어도, 네가 이 파일을 자동으로 읽고 매번 다시 설명하지 않아도 같은 방식으로 동작할 수 있어. 이 규칙을 확인했다고 나한테 짧게 알려주고, 지금부터 내가 요청하는 모든 파일 수정은 이 방식대로 진행해줘.
💡 팁 CLAUDE.md는 프로젝트(저장소)마다 따로 적용됩니다. 새 프로젝트 폴더를 시작하면 그 폴더에는 아직 이 파일이 없으니, 그 폴더에서 위 지침을 다시 한 번 붙여넣어야 해요. 그리고 "파일 지워줘"나 "이전 버전으로 되돌려줘" 같은 되돌리기 어려운 작업은 이 자동화 대상이 아니니, 그럴 땐 에이전트가 먼저 확인을 구하는 게 정상입니다.
🤖 바이브 코딩 제대로 하려면? — 에이전트 vs 채팅형 AI

결론부터 말하면… 계속 만드실 계획이면 Claude Code 결제 한번 고려해보세요 ㅋㅋ

에이전트(Agent)란 AI가 텍스트로 답만 하는 게 아니라, 실제로 컴퓨터의 터미널·파일·인터넷 브라우저 같은 "도구"를 직접 조작할 수 있는 AI를 말합니다. 대표적으로 Claude Code(Anthropic), Codex(OpenAI)가 있습니다. 반면 오늘 워크숍에서 쓴 제미나이·챗GPT·클로드의 "채팅 창"은 텍스트(와 이미지)만 주고받을 수 있을 뿐, 실제 실행(파일 저장, 배포 버튼 클릭 등)은 전부 사람이 대신해야 합니다.

🔥 Firebase로 갈아타기 — Apps Script의 "복붙 배포"가 사라진다

에이전트 + GitHub Pages를 쓰고 있다면 특히 추천

Apps Script는 Code.gs를 한 줄이라도 고치면, 그 코드를 통째로 복사해서 script.google.com 편집기에 붙여넣고, 저장하고, [배포 → 배포 관리 → 새 버전]까지 눌러야 진짜 반영됩니다. Firebase(Realtime Database)는 이 과정 자체가 없습니다 — 데이터를 저장/조회하는 규칙(보안 규칙)만 처음에 한 번 정해두면, 그 다음부터는 화면(HTML) 코드 안에서 바로 데이터베이스 주소로 요청을 보내면 됩니다. 즉 "따로 배포해야 하는 서버 코드"가 아예 없어서, 화면 코드를 고쳐서 GitHub에 올리는 것(git push)만으로 전부 끝납니다.

항목Apps Script + SheetsFirebase (Realtime Database)
백엔드 코드Code.gs (따로 작성/배포 필요)없음 — 보안 규칙만 최초 1회 설정
코드 수정 후 반영복사 → script.google.com 붙여넣기 → 새 버전 배포 (매번 반복)git push 한 번으로 끝
데이터 보는 곳Google Sheets (표, 익숙함)Firebase 콘솔 (JSON 트리 구조)
에이전트 자동화어려움 (OAuth 수동 승인 필요)쉬움 (REST로 curl 읽기/쓰기/삭제 바로 가능)
실시간 갱신직접 새로고침(polling) 필요실시간 리스너 지원
처음 설정 난이도스프레드시트 복사만 하면 됨 (쉬움)콘솔에서 프로젝트+DB+규칙 설정 (개념은 새롭지만 1회성)

아래 지침서를 통째로 복사해서 제미나이(또는 다른 AI 챗봇)에게 새 대화로 붙여넣으면, AI가 한 단계씩 안내해줍니다.

📋 지침서 펼쳐서 복사하기 ▼
너는 지금부터 코딩을 전혀 모르는 선생님이, Firebase Realtime Database를 새로 만들어서 자신의 html 페이지에 데이터를 저장/조회하는 기능을 연결하는 걸 도와주는 조수야. 아래 내용을 반드시 지켜서 진행해줘. [먼저 확인할 것] 지금 이 기능을 추가하려는 html 파일이 이미 있는지, 그리고 그 파일이 GitHub Pages 등으로 배포되어 있는지(주소가 있는지) 물어봐줘. [왜 이 방식을 쓰는지 — 필요하면 나한테 설명해줘] Apps Script는 코드를 고칠 때마다 script.google.com 편집기에 복사해서 붙여넣고 새 버전으로 재배포해야 하는데, Firebase는 그런 별도의 "서버 코드 배포" 과정이 없다. 데이터를 저장하는 규칙(보안 규칙)만 한 번 설정해두면, 그 다음부터는 화면 코드 안에서 바로 데이터베이스 주소로 요청을 보내면 되기 때문에, 화면 코드를 고쳐서 GitHub에 올리는 것(git push)만으로 전부 끝난다. [작업 순서 — 한 단계씩만 안내하고, 내가 완료를 확인해주면 다음으로 넘어가] 1) Firebase 프로젝트 만들기 - console.firebase.google.com 접속하라고 안내 - "프로젝트 추가" 클릭 → 프로젝트 이름 정하기 → 구글 애널리틱스는 켜든 끄든 상관없다고 알려주고 원하는 대로 진행 → 프로젝트 만들기 2) Realtime Database 만들기 - 왼쪽 메뉴 "빌드" → "Realtime Database" → "데이터베이스 만들기" 클릭하라고 안내 - 위치는 아무 곳이나 선택해도 된다고 알려주고, 규칙은 일단 "테스트 모드"로 시작하라고 안내 (테스트 모드는 30일 뒤 잠긴다는 것도 알려주고, 3번에서 직접 규칙을 설정할 거라고 안내) 3) 보안 규칙 설정하기 - "규칙" 탭으로 들어가서, 지금 만들려는 기능에 필요한 경로만 공개하는 규칙으로 바꿔주라고 안내. 아래 형태를 기본으로 내가 원하는 경로 이름에 맞게 채워서 줘: { "rules": { "내데이터경로": { ".read": true, ".write": true } } } - "게시" 버튼을 눌러야 실제로 적용된다고 반드시 알려줘. 4) 웹 앱 등록해서 연결 정보 받기 - 프로젝트 개요 페이지에서 웹 아이콘("</>" 모양)을 클릭해서 앱 등록하라고 안내 - 등록 후 나오는 firebaseConfig 객체(apiKey, databaseURL 등이 담긴 코드 조각)를 통째로 나한테 알려달라고 요청 5) 화면(HTML) 코드에 연결하기 - 받은 databaseURL을 이용해서, 데이터를 저장할 때는 fetch(databaseURL + "/경로.json", {method:"POST", body: JSON.stringify(데이터)})처럼, 불러올 때는 fetch(databaseURL + "/경로.json")처럼 쓰는 코드를 만들어줘 - 이 코드는 전부 화면(HTML) 파일 안에 들어가고, 별도로 배포할 서버 코드가 없다는 걸 나한테 알려줘 6) 테스트 - 실제로 데이터를 저장해보고, Firebase 콘솔의 "데이터" 탭에서 그 값이 쌓였는지 눈으로 확인해보라고 안내 [막히면 확인할 것 — 내가 아래 증상을 말하면 바로 원인을 알려줘] - 데이터 저장이 안 된다 → 3번의 보안 규칙에서 해당 경로가 write: true로 되어 있는지, "게시" 버튼을 눌렀는지 확인 - 30일 지나서 갑자기 안 된다 → 테스트 모드 기한 만료. 3번에서 규칙을 직접 설정해뒀으면 문제 없다고 알려줘 - 이후에 규칙이나 코드를 더 세밀하게 나누고 싶다 → 그때 다시 이 대화로 돌아와서 요청하면 된다고 알려줘 자, 이제 나한테 지금 어떤 화면(html)에 이 기능을 연결하고 싶은지부터 물어보는 것부터 시작해줘.

🤝 에이전트 + GitHub Pages 조합에서 진가를 발휘하는 이유

Claude Code 같은 에이전트를 쓰고 있다면 이 조합의 장점이 확실히 드러납니다. Apps Script는 배포 여부를 에이전트가 직접 확인할 방법이 마땅치 않아서, 코드를 고칠 때마다 결국 사람이 "복사해서 붙여넣고 새 버전으로 배포했어요"라고 확인해줘야 다음 단계로 넘어갈 수 있었습니다. Firebase는 REST 주소로 바로 데이터를 읽고 쓰고 지울 수 있어서, 에이전트가 터미널에서 직접 확인하고 정리까지 마친 뒤 결과만 보고합니다. 그리고 화면 코드를 고친 뒤에는 git push 한 번이면 GitHub Pages에도, Firebase 연결에도 동시에 반영되니 — "복사해서 어디에 붙여넣어야 하지"라는 그 한 단계가 통째로 사라집니다.

🆚 Firebase vs Supabase — 둘 다 데이터 저장하는 곳인데 뭐가 다를까?

맞습니다 — 둘 다 "백엔드"입니다. 서버를 직접 사서 켜두지 않아도 회사가 대신 서버를 운영해주면서, 데이터를 저장·조회해주는 서비스라는 점은 같습니다.

다른 점은 데이터를 담아두는 "모양"과, 그게 지금 이 워크숍 방식(GitHub Pages + AI)과 얼마나 잘 맞는지입니다.

항목Firebase (RTDB)Supabase
데이터 모양트리형 JSON — 폴더처럼 계속 안으로 들어가는 구조표(테이블) — 엑셀·구글시트처럼 행·열
화면 코드와 연결SDK 없이 주소 뒤에 .json만 붙여서 REST로 바로 읽고 쓰기 가능보통 클라이언트 라이브러리 설치 + RLS(행 단위 보안 규칙) 설정이 필요
무료 플랜 운영비활성 상태로 인해 절대 멈추지 않음7일간 요청 없으면 프로젝트가 자동으로 일시정지
비개발자가 배우기"그냥 큰 JSON 파일"이라는 설명 한 줄로 끝 — 진입장벽이 낮음표 화면 자체는 친숙하지만, RLS 개념은 확실히 어려움

지금처럼 "GitHub Pages + AI로 빠르게 만들고 배포"하는 흐름엔 Firebase가 더 잘 맞습니다. 다만 방학처럼 오래 안 쓰는 앱을 Supabase로 만든다면, 무료 플랜이 7일 뒤 자동으로 멈춘다는 점을 꼭 기억해두세요.

  • 좋아요·댓글 같은 상호작용 — 지금 이 갤러리에 쓰인 방식 그대로!
⚠️ 조금 어렵지만 도전해볼 만한 것
  • 이미지 업로드 — 사진 첨부 갤러리, 프로필 사진 등록
  • 검색·정렬·필터 — 이름으로 검색, 최신순/인기순 정렬
  • 권한을 나누는 기능 — 관리자 전용 화면 (오늘 만든 갤러리의 "삭제/수정" 정도는 충분히 도전 가능한 난이도예요)

  • 앱 안에 AI 기능 넣기 (자동 요약, 챗봇처럼 대답하기) — 별도 유료 API와 보안 지식이 필요해요
  • 진짜 실시간 기능 (입력 중 표시, 화상채팅) — 웹소켓이라는 다른 기술이 필요합니다
  • 결제(돈 받기) 기능 — 정식 결제대행사와 계약이 필요한 영역
  • 진짜 회원가입/로그인 시스템 (비밀번호 설정·찾기) — 보안 지식이 많이 필요해요
  • 앱스토어에 올라가는 네이티브 앱, 무거운 사진/영상 편집·AI 그림 생성
  • 데이터가 수만 건 이상으로 아주 많아지는 경우 — 이땐 진짜 데이터베이스가 필요해요
